## 2. Detailed Vulnerability & Hardening Notes

### SEC-UI-01: `PermissionGate.tsx` Client-Side Admin Permission Fallback

- **Observed Code (`apps/web-shell/src/components/admin/ui/PermissionGate.tsx:28-36`)**: Reads `(user as any).adminRoles` and `(user as any).adminPermissions`. Because `apps/api/src/modules/users/users.service.ts:30-41` (`GET /api/v1/users/me`) returns only `{ id, supabaseAuthId, email, firstName, lastName, avatarUrl, status, roles, createdAt, updatedAt }`, `adminPermissions` on the client is always `[]`. Thus `userRoles.includes('ADMIN') && (!adminPermissions || adminPermissions.length === 0)` evaluates `true` for every staff role.
- **Mitigation Status**: Authoritative backend RBAC (`fastify.requireAdminPermission(...)`) blocks unauthorized requests (`403`) on every endpoint and leaks zero audit rows (proven in Playwright Test `3.3`). Extending `/api/v1/users/me` or adding `/api/v1/admin/me` is recommended before relying on client `PermissionGate` for UX locking.

### SEC-AUD-03: Pre-Existing `admin-users.service.ts` Unsanitized Activity Metadata

- `GET /api/v1/admin/audit` runs `sanitizeAuditMetadata()` on every row before returning DTOs.
- Pre-existing `AdminUsersService.getUserActivity()` (`apps/api/src/modules/admin/users/admin-users.service.ts`) returns raw `l.metadata` directly from Prisma. Reusing `sanitizeAuditMetadata()` there is a straightforward one-function follow-up.

### SEC-API-01: Dispute Route Coarse Role Check

- `apps/api/src/modules/disputes/disputes.routes.ts` authorizes admin arbitration with `(request.user.roles || []).includes('ADMIN')` rather than fine-grained `requireAdminPermission(...)`, meaning any staff user with `RoleType.ADMIN` (such as `ANALYTICS_VIEWER` or `SUPPORT_ADMIN`) is permitted by the route to resolve disputes unless constrained further in a future RBAC milestone.
