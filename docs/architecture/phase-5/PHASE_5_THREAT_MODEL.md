# CreatorConnect — Phase 5 Security Threat Model (STRIDE)

## 1. Threat Modeling Methodology

This document establishes the comprehensive **STRIDE** (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) threat model for Phase 5 components.

Each threat is analyzed using the standardized 6-point matrix:
$$\text{Threat} \implies \text{Attack Vector} \implies \text{Impact} \implies \text{Mitigation} \implies \text{Detection} \implies \text{Recovery}$$

---

## 2. Exhaustive STRIDE Threat Analysis Matrix (23 Vectors)

| ID       | Threat                                | Attack Vector                                                                              | Potential Impact                                                      | Technical Mitigation                                                                                                              | Detection Mechanism                                                                                   | Recovery & Remediation                                                                      |
| :------- | :------------------------------------ | :----------------------------------------------------------------------------------------- | :-------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------ |
| **T-01** | **Token Theft**                       | Attacker intercepts JWT from insecure client storage or compromised proxy.                 | Full session impersonation.                                           | Short token lifetime (15m), HTTPS enforcement, strict cookie flags (`HttpOnly`, `SameSite=Lax`, `Secure`).                        | Prometheus alert on unexpected IP geolocation shift for user session.                                 | Revoke user refresh tokens; emit `platform:user_revoked` to terminate active sockets.       |
| **T-02** | **Token Replay**                      | Attacker captures expired or logged-out token and replays against API/Socket.              | Unauthorized actions using stale credentials.                         | Server checks `exp` and `nbf` claims; checks `user_status` and revocation blacklist in Redis.                                     | 401 `AUTH_TOKEN_EXPIRED` metrics spike in Pino structured logs.                                       | Deny request; client forced to re-authenticate with Supabase.                               |
| **T-03** | **WebSocket Hijacking**               | Cross-Site WebSocket Hijacking (CSWSH) via malicious web page.                             | Attacker opens socket to server utilizing victim credentials.         | Origin validation in Socket.IO handshake (`CORS_ORIGIN` matching); token passed via auth header/payload, not ambient cookies.     | Socket handshake rejection logged with unexpected `Origin` header.                                    | Malicious connection refused at handshake.                                                  |
| **T-04** | **Room Authorization Bypass**         | Client sends `socket.emit('conversation:join', { conversationId })` for arbitrary room.    | Eavesdropping on private conversations of other users.                | Server handler executes database query verifying user is an active participant before `socket.join()`.                            | Log warning: `UNAUTHORIZED_ROOM_JOIN_ATTEMPT` with actorId and target room.                           | Return 403 error ACK; reject room join.                                                     |
| **T-05** | **User Impersonation**                | Client submits `{ senderId: victimId }` in message payload.                                | Attacker poses as another creator or brand.                           | Server discards any client-supplied `senderId`; derives `senderId = socket.data.user.id` strictly.                                | Schema validation strips or rejects foreign fields; test asserts sender identity override impossible. | Message attributed solely to authenticated caller.                                          |
| **T-06** | **Message Spoofing**                  | Attacker injects fake sequence numbers or timestamps.                                      | Breaks chronological conversation timeline; displays deceptive order. | Sequence number generated server-side via PostgreSQL row lock on conversation; client sequence ignored.                           | Client sequence discarded; database sequence assigned.                                                | Monotonic ordering maintained.                                                              |
| **T-07** | **IDOR (Direct Object Reference)**    | Attacker guesses UUID of another user's conversation to read messages.                     | Unauthorized disclosure of private discussions and contracts.         | SQL query enforces `WHERE conversation_id = :id AND EXISTS (SELECT 1 FROM conversation_participants WHERE user_id = :actorId)`.   | 403 Forbidden logged on access attempt.                                                               | Query returns 0 rows or throws `ConversationAccessDeniedError`.                             |
| **T-08** | **Tenant Escape**                     | User from Brand A attempts to query conversations or assignments belonging to Brand B.     | Cross-tenant data leakage.                                            | CASL policy and scoped SQL filters enforce tenant boundary checks on every query.                                                 | Security audit log alert on cross-tenant ID access.                                                   | Query rejected with 403 Forbidden.                                                          |
| **T-09** | **Block Bypass**                      | Blocked user attempts to message blocker via alternative API route or direct socket event. | Harassment and platform abuse.                                        | Centralized `isBlocked(sender, recipient)` check executed before message creation and conversation invitation.                    | Audit log records blocked communication attempt.                                                      | 403 Forbidden (`USER_BLOCKED`) returned immediately.                                        |
| **T-10** | **Attachment Malware**                | Attacker uploads Trojan, spyware, or malicious script disguised as a PDF/image.            | Infection of peer devices opening the attachment.                     | Direct upload lands in quarantine bucket; scanned via ClamAV daemon (`INSTREAM`); rejected if infected.                           | ClamAV returns `stream: FOUND <virus>`; audit log records malware attempt.                            | Quarantined object purged; asset marked `REJECTED_INFECTED`; user flagged for moderation.   |
| **T-11** | **Malicious Payload / Stored XSS**    | Attacker submits `<script>` tags or HTML entities in message content.                      | Script execution in victim's browser session.                         | Next.js React frontend auto-escapes string content; server validates plain text schema and sanitizes input.                       | WAF / API logs detect HTML tags in message payload.                                                   | Content rendered safely as raw text nodes.                                                  |
| **T-12** | **Oversized Payload / DoS**           | Attacker posts 10MB text blob in message content or sends 10,000 attachments.              | Database buffer pool exhaustion, network saturation.                  | Fastify `bodyLimit` (1MB); TypeBox schema limits message length to 4,000 chars, max 5 attachments.                                | Fastify 413 Payload Too Large / TypeBox validation error.                                             | Request terminated at parser stage before hitting database.                                 |
| **T-13** | **Spam / Message Flooding**           | Automated bot emits 100 messages per second.                                               | Degrades realtime node performance and floods recipient inboxes.      | Dual-key Redis sliding-window rate limit (5 msgs/sec per user).                                                                   | Rate limiter triggers; 429 Too Many Requests returned.                                                | Excess messages dropped; repeat offender auto-muted.                                        |
| **T-14** | **Notification Abuse**                | Attacker spams actions that trigger push notifications to harass victim.                   | Battery drain, notification spam, FCM quota depletion.                | Notification dispatch checks per-user rate limit (max 10 push/hour from same sender).                                             | BullMQ notification throttle skips redundant push jobs.                                               | Notifications coalesced into single digest.                                                 |
| **T-15** | **Redis Compromise**                  | Attacker gains access to Redis instance.                                                   | Eavesdropping on presence; tampering with rate limit counters.        | Redis requires password (`requirepass`); TLS in production; Redis contains no passwords or business data; AOF enabled.            | Redis AUTH failure alerts; network VPC isolation.                                                     | Rotate Redis password; flush ephemeral presence; PostgreSQL authoritative state unaffected. |
| **T-16** | **Outbox Tampering**                  | Attacker injects fake events directly into `outbox_events`.                                | Triggering unauthorized side-effects and external notifications.      | PostgreSQL permissions restrict `INSERT/UPDATE` on `outbox_events` to authenticated application DB user only.                     | Database audit logs monitor write origins.                                                            | Foreign events rejected by consumer schema validators.                                      |
| **T-17** | **Event Replay**                      | Attacker replays intercepted outbox event payload to consumer queue.                       | Duplicate notifications or duplicate status changes.                  | Consumers check `processed_events` table (`UNIQUE(eventId, consumerName)`); duplicate executions no-op.                           | Consumer logs record duplicate event suppressed.                                                      | Zero double-mutations.                                                                      |
| **T-18** | **Duplicate Request Retries**         | Network timeout causes client to re-send message send request.                             | Duplicate message appearing in conversation thread.                   | Enforce `UNIQUE(sender_id, conversation_id, client_message_id)`; returns original message on collision.                           | Database P2002 unique constraint caught safely by service.                                            | Exactly one message persisted and sequenced.                                                |
| **T-19** | **Race Conditions (Sequence)**        | Two users send messages to the same conversation simultaneously.                           | Sequence collision or out-of-order sequence assignment.               | PostgreSQL `SELECT FOR UPDATE` on conversation row serializes sequence assignment.                                                | Postgres transaction lock metrics monitored for contention.                                           | Transactions execute sequentially; zero gaps in sequence.                                   |
| **T-20** | **Connection Flooding (DoS)**         | Attacker opens 50,000 concurrent WebSocket connections.                                    | Exhausts server memory and file descriptors.                          | Rate limit on handshake per IP (max 20 connects/min); OS `somaxconn` tuned; ALB ingress limits.                                   | Cloudflare / ALB alerts on high connection churn.                                                     | Attacking IPs banned at firewall.                                                           |
| **T-21** | **Rate-Limit Bypass via IP Spoofing** | Attacker rotates `X-Forwarded-For` header to bypass IP rate limits.                        | Flooding API unhindered.                                              | `proxy-addr` overrides configured to trust strictly internal ALB/ingress CIDRs; untrusted headers stripped.                       | Rate limiter primary key uses authenticated `usr:<userId>` whenever token is present.                 | Rate limits enforced against user ID regardless of IP.                                      |
| **T-22** | **Proxy IP Spoofing (IPv4-Mapped)**   | Attacker sends `::ffff:127.0.0.1` to bypass rate limits as loopback.                       | Bypasses local rate limit checks.                                     | `proxy-addr` pinned to `>=2.0.8` (GHSA-jqcg-44mw-7w3h patched); regression tests in CI.                                           | Unit tests in `rate-limit.spec.ts` enforce proper subnet parsing.                                     | Spoofed header ignored.                                                                     |
| **T-23** | **Private Media Leakage**             | Attacker discovers storage key of a private chat attachment.                               | Confidential document exposed.                                        | Cloudflare R2 bucket is private (public read disabled); download requires signed URL with 15m expiry issued only to participants. | Cloudflare R2 access logs monitored for 403 unauthorized bucket scans.                                | Direct bucket access denied.                                                                |
