1. Purpose and Scope of This Document

This document is the single authoritative reference for the CreatorConnect Admin Panel. It captures every data entity the platform manages, every administrative workflow that must be supported, every screen, action, filter, status lifecycle, and business rule that the development team needs to implement in the backend APIs and the web-based Admin Panel UI.

It serves three audiences simultaneously:

  • Developers — every table, field, status enum, and API endpoint is explicitly specified before a line of code is written.
  • Designers — every screen's required data columns, action buttons, filter options, and empty states are enumerated.
  • Client (Anjana / CreatorConnect) — the delivered system can be verified against this specification during UAT.

The scope covers the full Admin Panel described in the CreatorConnect Statement of Work (Codly360, 2026): User Management, Verification, Assignment Management, Content Moderation, Review Management, Subscription Management, Payment Management, Referral Management, Notification Management, Analytics & Reporting, Dispute Management, and all Platform Configuration and System Settings.

This document does not cover the mobile application, user-facing web application, or the backend API architecture in detail — those are addressed in separate specification documents.

2. Admin Roles and Access Control (RBAC)

The Admin Panel must support role-based access control (RBAC). Not every person who accesses the Admin Panel should be able to see payment data, delete content, or change platform configuration. The following roles must be implemented from day one, with the architecture supporting addition of new roles in future without code changes.

2.3 Audit Log Requirements

Every destructive or consequential admin action must be recorded in an immutable audit log. Each entry must capture:

  • Timestamp (UTC, millisecond precision)
  • Admin user ID and display name
  • Admin role at time of action
  • Action type (e.g. USER_SUSPENDED, VERIFICATION_APPROVED, PAYMENT_REFUNDED)
  • Target entity type and ID (e.g. user_id: 12345)
  • Previous state — JSON snapshot of changed fields before the action
  • New state — JSON snapshot after the action
  • IP address and device/browser of the admin session
  • Optional reason/comment entered by the admin

  • Open disputes with no admin response in 24 hours
  • User accounts auto-flagged by the system (e.g. multiple reports in 24h)

Scrollable list of the last 50 platform-wide user events, newest first. Each row shows: timestamp, event type, actor (display name + role), and a brief description. Clicking a row opens the relevant admin detail screen.

4.3.1 Suspension Workflow

When an admin clicks "Suspend", a modal dialog appears with these required fields:

  • Reason (dropdown): Spam, Harassment, Fake Account, Verification Fraud, Payment Fraud, Repeated Policy Violations, Under Investigation, Other
  • Additional Notes (textarea, optional but encouraged)
  • Duration: Temporary (1 / 3 / 7 / 14 / 30 days / Custom dates) or Indefinite
  • Notify User (toggle, default ON) — sends in-app notification and email with reason and expected lift date
  • Confirm: Admin must retype the user's username to confirm

The system automatically lifts temporary suspensions at the specified end time and restores status to "active" without requiring further admin action.

4.3.2 Ban Workflow

Banning is permanent and requires additional safeguards:

  • Mandatory "Reason for Permanent Ban" text field — minimum 20 characters.
  • The system adds the user's email and phone to a blocklist table to prevent re-registration.
  • Requires approval from a second admin if the acting admin is below Super Admin level (two-party authorisation).
  • Confirmation dialog requires the admin to type "BAN [username]" exactly.

5.2.3 Decision Actions

  1. Approve — Verification badge applied to public profile immediately. User notified.
  2. Reject — Requires a rejection reason (dropdown) and an explanatory message shown to the user.   4. Escalate — Assigns to a Senior Admin with an escalation note.

7.3 Automated Moderation Triggers

  • 3 or more unique users report the same content within 24 hours → content auto-hidden pending admin review
  • A user receives 5 or more reports in 7 days → account status auto-set to "under_review", admin notified
  • Content containing a blocklisted keyword (admin-configurable) → auto-flagged for review before publication
  • Chat message containing phone number, email, or URL in the first 3 messages of a new conversation → flagged (anti-bypass control)
  • Profile bio containing contact information or external links → flagged for review before profile is made public

8.2 Review Abuse Detection — Auto-Flag Rules

  • Reviewer and reviewee have no completed assignment connecting them → "No prior collaboration detected"
  • Reviewer submits 3 or more reviews in a 24-hour window → "High review velocity"
  • Multiple reviews from the same IP address within 1 hour → "Same-IP cluster"
  • 1-star review submitted within 1 hour of a dispute being opened → "Dispute-correlated"
  • Review contains contact information, URLs, or competitor names → "Spam content"

10.2 Refund Workflow

  1. Admin clicks "Issue Refund" on a transaction.
  2. Modal shows: original amount, eligible refund amount, reason dropdown (Customer Request / Fraud / Duplicate Payment / Technical Error / Admin Goodwill / Other), and an optional note.
  3. Admin confirms. Backend calls the Razorpay Refund API.
  4. Transaction status updates to "Refunded" on Razorpay confirmation. If it fails, admin sees the error and must retry or contact Razorpay.
  5. User is notified of the refund via in-app notification and email (notification toggle on the refund modal).
  6. Refund action is logged in the audit log with reason.

10.3 Revenue Dashboard Metrics

  • Total Revenue (MTD) — gross payments captured this month
  • Total Revenue (Last 30d) — rolling 30-day window
  • Revenue by Plan — which subscription plans are generating revenue (pie chart + table)
  • Revenue by Payment Method — UPI vs Card vs NB vs Wallet (bar chart)
  • Daily Revenue Chart — bar chart for the last 30 days
  • Refund Rate — (total refund amount / total captured amount) × 100
  • Failed Payment Rate — (failed count / total attempted count) × 100
  • MoM Growth — % change in revenue vs. previous calendar month
  • Export — CSV or PDF download

11.3 Fraud Detection Rules

  • More than 5 referrals from the same IP address
  • Referred users who register but never log in after registration ("ghost accounts")
  • Referred users whose phone OTP verification fails multiple times
  • Referrer who generates more than 20 referrals in a single day
  • Referred users who share the same device fingerprint as the referrer
  • Reward claimed but referred user's account deactivated within 7 days of qualifying

12. Notification Management Module

12.1 Notification Composer

Recipient Selection

All users, specific role(s), specific membership plan(s), specific users (search/bulk paste), users matching a saved filter, geographic segment (state or city).

Channel Selection

Push Notification (FCM), In-App Notification, Email — any combination of these three.

Content Fields

  • Title (max 65 characters for push compatibility)
  • Body / Message (up to 500 characters for push; unlimited for email)
  • Deep Link / CTA URL — the screen the notification navigates to when tapped (optional)

Scheduling

Send now, schedule for later (date + time picker), or send in user's local timezone (useful for "good morning" type notifications — FCM sends at the specified clock time in each user's local timezone).

Preview Requirement

Before sending, the admin must see a preview panel showing how the notification will look on Android (push + in-app), iOS (push + in-app), and in email. Required to prevent formatting errors reaching all users.

All Admin Panel interactions must go through dedicated, authenticated admin API endpoints on the Fastify backend. Admin endpoints must be clearly namespaced at /api/admin/... and must never share route handlers with the user-facing API.

All admin API endpoints must: require a valid admin JWT (issued only via /api/admin/auth/login), enforce RBAC middleware matching the permission matrix in Section 2.2, and write to the audit log on any state-changing operation.

18.4 Remaining Module APIs (Pattern)

The following modules each require a standard set of endpoints following the same pattern (GET list with filters, GET detail, PATCH for actions, POST for creation where applicable):

  • Assignments: /api/admin/assignments — includes feature, force-status changes, removal.
  • Applications: /api/admin/applications — includes admin endorsement or flag.
  • Reports (Moderation): /api/admin/reports — includes all moderation decision endpoints.
  • Reviews: /api/admin/reviews — includes hide, unhide, delete, flag.
  • Subscriptions: /api/admin/subscriptions — includes cancel, extend, grant-complimentary, change-plan.
  • Payments: /api/admin/payments — includes refund initiation (calls Razorpay API), download receipt.
  • Referrals: /api/admin/referrals — includes manual reward issuance and fraud-flag.
  • Notifications: /api/admin/notifications — compose (POST), schedule (POST), log (GET), templates (GET/PATCH).
  • Disputes: /api/admin/disputes — includes assign, respond, resolve.
  • Analytics: /api/admin/analytics/:metric — parameterised analytics endpoints returning aggregated data.
  • Config: /api/admin/config/* — feature flags, plans, categories, moderation settings.
  • Audit Log: /api/admin/audit-log — paginated, filterable, read-only.

19. Technical and Non-Functional Requirements

19.1 Admin Panel Technology

  • Framework: React (Next.js) or plain React — consistent with the web application where possible to allow code sharing.
  • UI Component Library: A mature component library recommended (e.g. Ant Design Pro, shadcn/ui + Tailwind) to accelerate development of data-heavy admin UIs.
  • Authentication: Separate admin user table with JWT issued by the Fastify backend. Admin accounts are distinct from user accounts.
  • Hosting: Vercel or separate deployment as per final architecture decision.

19.2 Security Requirements

  • 2FA is mandatory for all admin accounts. TOTP (Google Authenticator compatible). No admin login without 2FA.
  • Session timeout: Admin sessions expire after 4 hours of inactivity; active sessions expire after 12 hours regardless.
  • IP allowlisting: Super Admin access should optionally require IP whitelisting (configurable). If the requesting IP is not on the whitelist, the Super Admin account cannot be accessed.
  • All admin API calls must be over HTTPS with valid SSL certificate (via Cloudflare).
  • Password requirements: Minimum 12 characters, at least one uppercase, one lowercase, one digit, one special character.
  • Brute-force protection: Account locked for 15 minutes after 5 consecutive failed login attempts. Super Admin is notified by email of any lockout.
  • The admin panel frontend must never expose a full user email, phone, or government ID number in the browser DOM without an explicit "reveal" action that is logged in the audit log.

19.3 Performance Requirements

  • All list views must load in under 2 seconds for datasets up to 100,000 records. All queries must use appropriate database indexes.
  • All list views must implement server-side pagination (default 25 records per page, max 100 per page). No client-side pagination over large datasets.
  • Dashboard KPI cards must load in under 1 second. Use Redis (Upstash) caching for aggregated analytics data with a TTL of 5 minutes.
  • File downloads (CSV exports, PDF receipts) must be generated asynchronously for large datasets (>1,000 rows) — the admin is shown a progress indicator and receives a download link when ready.

19.4 Accessibility and Usability

  • Fully usable on desktop (1280px+) and reasonably usable on tablet (768px+). Mobile responsiveness is not required for the admin panel.
  • All tables must support keyboard navigation.
  • All destructive actions (delete, ban, refund) must require a confirmation step — either a confirmation dialog or typing a specific string.
  • All bulk actions must display a summary ("You are about to suspend 47 users. This will…") before executing.
  • All forms must have clear error states with specific messages (not generic "Something went wrong").
